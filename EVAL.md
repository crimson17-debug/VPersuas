# Evaluation

Generated by `npm run eval`. Reproducible: every stochastic step is seeded,
so these numbers are identical on any machine.

- Corpus: **200** labelled 48-hour windows
- Warm-up split: **60** (engine starts with zero priors)
- Held-out split: **140** (all figures below)
- Priors earned during warm-up: 9536 treated, 17980 held-out observations
- Wall clock: 70.8s

The engine never imports the ground-truth world model. `npm run check:boundaries`
fails the build if it does.

## The headline

| | |
|---|---|
| Gross recovered (what a system with no holdout would claim) | **₹44.05L** |
| Recovery rate, treated arm | 54.5% (n=3383) |
| Recovery rate, holdout arm | 35.4% (n=4529) |
| Measured lift | **19.2pp** |
| Incremental recovered | **₹14.88L** (95% CI ₹13.19L – ₹16.58L) |
| Share of the gross figure that was never caused | **66.2%** |
| Spend | ₹5.29L |
| Net value created | **₹9.60L** (lower bound ₹7.90L) |

Across 140 held-out windows the engine acted on 3383
items out of 32341 at risk, and 991 were stopped by
compliance rules before anything was sent.

Incremental value is pooled across the whole run rather than summed from
per-window estimates. A single window holds out twenty or thirty items, so the
lift measured inside one window is mostly noise; adding up 140 noisy estimates
produces a total whose standard error runs to lakhs. Pooling the arms first and
dividing once gives one estimate with one interval that means something.

## Against baselines

Every baseline runs the identical execution, holdout, cost and measurement path,
and sees **all** at-risk items rather than only the ones this detector flagged.

| Policy | Gross claimed | Lift | Incremental (95% CI) | Spend | Net | Items touched |
|---|---:|---:|---:|---:|---:|---:|
| **This engine** | ₹44.05L | 19.2pp | ₹14.88L (₹13.19L–₹16.58L) | ₹5.29L | **₹9.60L** | 3383 |
| Nudge every failed payment | ₹65.65L | 3.6pp | ₹5.31L (₹3.30L–₹7.32L) | ₹18.6k | ₹5.13L | 6198 |
| Discount every failed payment | ₹71.41L | 7.4pp | ₹10.79L (₹8.77L–₹12.81L) | ₹10.90L | -₹10.5k | 6198 |
| Retry every failed payment immediately | ₹258.12L | 0.6pp | ₹3.74L (-₹4.59L–₹12.07L) | ₹26.0k | ₹3.48L | 26001 |
| Do nothing, ever | ₹0 | — | — | ₹0 | ₹0 | 0 |
| Pick an intervention at random | ₹152.89L | 2.7pp | ₹9.42L (₹5.68L–₹13.16L) | ₹4.03L | ₹5.39L | 14320 |

Read this table honestly:

- Nudge-everything claims **₹65.65L** gross and delivers
  **₹5.31L** incremental for ₹18.6k of spend.
  Its gross figure is the number a dashboard would print.
- Discount-everything claims ₹71.41L and nets
  -₹10.5k, because the discount is paid on every recovery
  including the ones that needed no help.
- Do-nothing spends nothing and creates nothing measurable. It is the floor every
  other policy has to clear, and on the null windows it is the correct policy —
  which is why this engine matches it there rather than trying to beat it.

An interval that spans zero in this table is not a rounding artefact. It means
that policy cannot be shown to have worked at this sample size, and reporting it
as a win would be the exact error this project exists to point at.

## Detection

- Precision: 100.0% (71/71, 95% CI 94.9%–100.0%)
- Recall: 64.5% (71/110, 95% CI 55.3%–72.9%)
- **False positives on null windows: 0.0% (0/30, 95% CI 0.0%–11.4%)**

The null windows contain nothing but ordinary daily variation, and half of them
ship a checkout release anyway so that "a release happened" is never on its own
enough to convict. Several hundred cohorts are tested per window, so the
significance threshold is Šidák-corrected for the number of tests actually run.

### Recall by cause

An aggregate recall number hides blind spots, so here is where the misses are.

| True cause | Detected | Windows | Recall |
|---|---:|---:|---:|
| Checkout regression | 13 | 16 | 81.3% |
| Customer abandonment | 9 | 15 | 60.0% |
| Gateway degradation | 9 | 15 | 60.0% |
| Issuer degradation | 14 | 19 | 73.7% |
| Payment-method mismatch | 3 | 16 | 18.8% |
| Retry timing | 12 | 18 | 66.7% |

Misses concentrate in the low-severity, broad-cohort incidents — a shallow
conversion decline spread thinly across a large cohort does not clear a
multiple-comparison-corrected threshold, and lowering that threshold to catch
them would put false positives back on the null windows. That trade is the
detector's single most consequential setting and it is deliberately tuned
toward silence.

## Abstention

- Null windows left completely alone: **30/30** (100.0%)
- Ambiguous windows where the engine returned insufficient evidence: **1/11** (9.1%)

Ambiguous windows contain two real causes at once — an issuer wobble and a
checkout regression starting within an hour of each other on overlapping traffic.
The affected cohort then carries a mix of failure reasons and no hypothesis can
take a majority of the evidence. There is a correct answer and it is not a cause:
it is "these cannot be separated". Naming either one confidently would be wrong
even on the windows where it happens to match the larger incident, which is why
these windows are excluded from the root-cause accuracy above.

## Speed

Median time from raw events to a decision: **130ms** (p95 188ms),
over roughly 4,000–6,000 events and several hundred cohort tests per window.

## What this evaluation does not prove

- The event history is synthetic. These numbers measure the engine against a
  simulator, not against production traffic, and no claim about real-world revenue
  lift follows from them.
- Cost and uplift structures are assumptions. They are plausible and they are
  stated in the open, but they are assumptions.
- Difference-in-differences assumes treated and control cohorts would have moved
  in parallel absent the cause. That assumption is checked in the pre-period and
  it can still be wrong.
